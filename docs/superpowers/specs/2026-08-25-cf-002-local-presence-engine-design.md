# CF-002 Local Presence Engine — Design

Date: 2026-08-25
Status: proposed implementation contract
Target: `delivery-ledger/reference-systems/local-presence-engine/`

## Purpose

Create a small, public, clean-room reference system that demonstrates production-shaped engineering judgment with inspectable code, tests, persistence, architecture, failure handling, and privacy-by-design.

The reference system is inspired only by generic engineering patterns already proven useful in private work. It must not disclose or reconstruct the private repository, client environment, real-world deployment, proprietary configuration, or confidential domain details.

## Public-safety contract

The implementation MUST NOT include:

- any private source copied from `garage_time` or any other private repository;
- private commit hashes, file paths, package names, class names, schema names, internal identifiers, comments, or documentation excerpts;
- real business names, garage names, people, addresses, camera details, plate values, images, or operational data;
- real secrets, tokens, API keys, URLs, hostnames, infrastructure configuration, or deployment topology;
- a reconstruction of proprietary architecture beyond generic patterns that would be independently reasonable for this reference problem.

The implementation MUST use only:

- generic concepts such as `ENTRY`, `EXIT`, `visit`, `event`, `opaque token`, and `anomaly`;
- deterministic synthetic data;
- newly written clean-room code;
- public documentation that explicitly states the system is a reference implementation, not the private production/pilot codebase.

## Problem statement

A local system receives synthetic passage events and must maintain a durable record of whether an anonymous entity is currently present.

Each event contains:

- a direction: `ENTRY`, `EXIT`, or `UNKNOWN`;
- an event timestamp in UTC;
- one or more opaque candidate tokens, or no token when evidence is unreadable;
- a source event identifier used for idempotency.

The system must update durable presence state deterministically while avoiding storage of raw identifiers.

## Scope

### In scope

1. Pure decision logic for matching an event against currently open visits.
2. Explicit anomaly classification for ambiguous or invalid inputs.
3. SQLite persistence with foreign keys and transaction boundaries.
4. Atomic processing of one event into one durable outcome.
5. Idempotent re-processing of an already handled source event.
6. Restart recovery demonstrated by closing and reopening the SQLite database.
7. Synthetic event generation and a CLI/demo path.
8. Unit tests for pure decision logic.
9. Integration tests for persistence, idempotency, restart recovery, and rollback behavior.
10. Architecture documentation and at least two ADRs.
11. A CF-002 casefile explaining what the reference system proves and what it deliberately does not claim.

### Out of scope

- cameras, OCR, computer vision, license-plate recognition, or image processing;
- Raspberry Pi or hardware integration;
- networking, cloud services, external APIs, web UI, or mobile UI;
- real authentication or user accounts;
- production deployment automation;
- performance benchmarking beyond basic deterministic tests;
- any claim that the reference system is identical to a deployed private system.

## Architecture

The reference implementation will use four explicit layers:

1. **Domain** — pure value objects and state-transition decisions. No SQLite imports.
2. **Application** — orchestration of one accepted event using repository/transaction interfaces.
3. **Infrastructure** — SQLite schema, connection setup, transaction implementation, and repositories.
4. **Interface** — a minimal CLI that runs a synthetic scenario and prints non-sensitive state transitions.

Dependency direction is inward: interface and infrastructure may depend on application/domain; domain must not depend on infrastructure.

## Core domain model

### Event

Fields:

- `event_id`: UUID generated by the reference application;
- `source_event_id`: non-empty synthetic string, unique for idempotency;
- `direction`: `ENTRY | EXIT | UNKNOWN`;
- `occurred_at_utc`: timezone-aware UTC datetime;
- `candidate_tokens`: immutable tuple of opaque token values.

### Opaque token

A token is a fixed-length digest-like byte value generated from synthetic input. Raw identity is never stored.

The reference system does not claim cryptographic privacy guarantees for real-world deployments; it demonstrates the architectural principle of separating raw identifiers from persisted matching evidence.

### Visit

A visit has:

- `visit_id`;
- `state`: `OPEN | CLOSED`;
- entry timestamp;
- optional exit timestamp;
- optional duration.

### Decision

The pure decision engine returns exactly one of:

- `OPEN_VISIT`;
- `CLOSE_VISIT`;
- `NO_CHANGE` with an anomaly.

Expected anomalies:

- `UNKNOWN_DIRECTION`;
- `UNREADABLE_EVENT`;
- `ENTRY_WHILE_OPEN`;
- `UNMATCHED_EXIT`;
- `AMBIGUOUS_MATCH`;
- `INVALID_TIMESTAMP_ORDER`.

## Deterministic matching rules

1. `UNKNOWN` direction never mutates presence and raises `UNKNOWN_DIRECTION`.
2. An event with no candidate tokens never mutates presence and raises `UNREADABLE_EVENT`.
3. An `ENTRY` with no matching open visit opens a new visit.
4. An `ENTRY` matching any open visit does not open another visit and raises `ENTRY_WHILE_OPEN`.
5. An `EXIT` matching no open visit raises `UNMATCHED_EXIT`.
6. An `EXIT` matching more than one open visit raises `AMBIGUOUS_MATCH` and must not choose arbitrarily.
7. An `EXIT` with exactly one matching open visit closes that visit.
8. If the exit timestamp precedes the visit's entry timestamp, the event is classified as `INVALID_TIMESTAMP_ORDER`; the implementation must preserve deterministic behavior and record the anomaly without manufacturing a negative duration.

## Persistence model

SQLite is used because it makes local durability inspectable without external infrastructure.

Required tables:

- `events` — durable source events and processing outcome;
- `event_tokens` — opaque tokens associated with pending events;
- `visits` — open/closed presence intervals;
- `visit_tokens` — opaque tokens for currently open visits;
- `anomalies` — explicit anomaly records.

Database invariants should be enforced by both application tests and SQLite constraints where reasonable.

Connection configuration should enable:

- foreign keys;
- WAL journal mode;
- an explicit busy timeout.

The design does not depend on a specific synchronous durability level; the implementation should choose and document one rather than imply a production guarantee.

## Transaction semantics

Processing one event must occur in a single explicit database transaction:

1. load the durable event;
2. if already processed, return the stored outcome without duplicating effects;
3. load open visits and their opaque tokens;
4. compute the pure domain decision;
5. apply visit/anomaly mutations;
6. mark the event processed;
7. commit atomically.

On any failure before commit, the transaction rolls back and the event remains safely retryable.

## Restart recovery

A test must:

1. create a temporary file-backed SQLite database;
2. process a synthetic `ENTRY`;
3. close the connection/process boundary;
4. reopen the database using a new application instance;
5. process the matching synthetic `EXIT`;
6. verify the original visit closes correctly.

This demonstrates durability and reconstruction from persisted state without claiming hardware-level fault tolerance.

## Synthetic demo

A single command should execute a deterministic scenario such as:

1. readable ENTRY → visit opened;
2. duplicate source event → idempotent same outcome;
3. second ENTRY with same token → anomaly;
4. matching EXIT → visit closed;
5. unmatched EXIT → anomaly;
6. print final visits and anomalies using only synthetic identifiers.

No real data is accepted or bundled.

## Testing strategy

Implementation is test-first.

### Unit tests

Must cover:

- no match;
- unique match;
- ambiguous match;
- entry opens visit;
- duplicate entry anomaly;
- unmatched exit anomaly;
- ambiguous exit anomaly;
- unknown direction;
- unreadable event;
- invalid timestamp ordering;
- deterministic ordering of matched visit IDs.

### Integration tests

Must cover:

- schema creation;
- foreign keys enabled;
- one entry/exit lifecycle;
- idempotent duplicate source event;
- atomic rollback on an injected failure;
- restart recovery using a file-backed database;
- persisted records contain no raw synthetic identity string after tokenization.
